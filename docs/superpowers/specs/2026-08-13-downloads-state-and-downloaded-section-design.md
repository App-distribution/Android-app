# Восстановление состояния загрузки и раздел «Скачанные»

Дата: 2026-08-13

## Контекст

Обратная связь от пользователя:

1. При нажатии «Установить», затем «Назад», затем возврате на экран сборки вместо индикатора загрузки показывается кнопка, и её нельзя нажать.
2. Куда деваются установочные файлы? Нужно либо удалять их после установки, либо сделать раздел «Скачанные».

По второму пункту принято решение: **раздел «Скачанные» с ручным удалением каждого файла и кнопкой «Очистить всё». Автоудаления нет.**

Жёсткое требование: изменения не должны ломать уже собранное и работающее приложение.

## Корневая причина бага №1

Два связанных дефекта.

**A. Состояние загрузки живёт только в памяти ViewModel.**
`BuildDetailUiState.downloadState` инициализируется как `Idle`, а `init` вызывает только `loadBuild()`. Навигация «Назад» уничтожает ViewModel; при возврате создаётся новая с `Idle`, и никто не переподписывается на идущую работу WorkManager. Индикатор пропадает, вместо него появляется кнопка.

**B. Работа отслеживается по UUID запроса, а не по имени.**
`DownloadBuildUseCase` ставит работу через `enqueueUniqueWork("download_$buildId", ExistingWorkPolicy.KEEP, request)`, после чего подписывается на `getWorkInfoByIdFlow(request.id)`.

`KEEP` означает: если незавершённая работа с таким именем уже есть, новый `request` отбрасывается и в БД WorkManager не попадает. Подписка идёт на UUID, которого не существует, flow бесконечно отдаёт `null`, ветка `else -> DownloadState.Idle` не меняет состояние. Нажатие кнопки не даёт никакого видимого эффекта — это и есть «кнопку нельзя нажать».

## Выбранный подход

Наблюдение по имени уникальной работы (`getWorkInfosForUniqueWorkFlow`) плюс `DownloadDao` как источник правды о готовом файле на диске. WorkManager отвечает за то, что происходит сейчас; Room — за то, что лежит на диске. Раздел «Скачанные» требует персистентного списка файлов в любом случае, так что второй источник не является лишней сущностью.

Отвергнутые варианты:

- Singleton-holder состояний в памяти — не переживает смерть процесса и дублирует то, что WorkManager уже хранит.
- Только Room как источник правды — при убийстве процесса воркера строка навсегда застревает в состоянии `downloading`, требуется отдельный механизм сверки.

## Инварианты обратной совместимости

Список того, что менять нельзя, и почему. Каждый пункт проверяется при реализации.

| Инвариант | Причина |
|---|---|
| Имя уникальной работы `download_$buildId` | Работа, поставленная в очередь до обновления, должна продолжать наблюдаться новым кодом |
| FQN класса `com.appdist.feature.builddetail.data.DownloadWorker` | WorkManager хранит имя класса воркера в своей БД. Перенос класса в другой модуль сделает невозможным инстанцирование уже поставленных в очередь работ, и они завершатся с FAILED |
| Ключи `inputData` воркера (`KEY_BUILD_ID`, `KEY_DOWNLOAD_URL`, `KEY_FILE_SIZE`, `KEY_EXPECTED_CHECKSUM`) | Читаются работами, поставленными в очередь до обновления |
| Путь файла `cacheDir/apk_downloads/<buildId>.apk` | Уже скачанные файлы должны остаться доступными; на этот путь завязан `file_paths.xml` |
| Authority FileProvider `${packageName}.fileprovider` и содержимое `file_paths.xml` | Ломает выдачу URI установщику |
| Имя БД `appdist.db`, имя таблицы `downloads`, первичный ключ `buildId` | Данные существующих установок |
| Значение `state = 'completed'`, записанное старым воркером, читается как «готово» | Строки, созданные до обновления |

Отдельно: миграция БД должна быть настоящей (`ALTER TABLE`), а не разрушительной. `fallbackToDestructiveMigration()` в `DatabaseModule` остаётся как страховка от падения на неожиданной схеме, но не должен срабатывать на пути 1 → 2.

## Модель данных

### DownloadEntity

Добавляются поля, чтобы раздел «Скачанные» не показывал UUID сборки, как сейчас делает `MineScreen`:

- `versionName: String` — default `''`
- `versionCode: Long` — default `0`
- `channel: String` — default `''`
- `completedAt: Long?` — nullable

Набор состояний приводится к единому: `downloading` / `verifying` / `ready` / `failed`. Сейчас воркер пишет `completed`, а `MineScreen` ожидает `ready` — из-за рассинхрона в UI показывается сырая строка `completed`.

### Миграция 1 → 2

```sql
ALTER TABLE downloads ADD COLUMN versionName TEXT NOT NULL DEFAULT '';
ALTER TABLE downloads ADD COLUMN versionCode INTEGER NOT NULL DEFAULT 0;
ALTER TABLE downloads ADD COLUMN channel TEXT NOT NULL DEFAULT '';
ALTER TABLE downloads ADD COLUMN completedAt INTEGER;

UPDATE downloads SET state = 'ready', completedAt = startedAt
  WHERE state = 'completed' AND localPath IS NOT NULL;
UPDATE downloads SET state = 'failed'
  WHERE state = 'completed' AND localPath IS NULL;
```

Строки, созданные старой версией, получают пустые `versionName` / `channel` и `versionCode = 0`. UI обязан это пережить — см. раздел «Деградация для старых записей».

Для возможности написать тест миграции в `core/database` включается `exportSchema = true`, а в `build.gradle.kts` добавляется ksp-аргумент `room.schemaLocation` с каталогом `core/database/schemas`. Схема `1.json` генерируется **до** изменения сущностей, чтобы точно соответствовать уже выпущенной версии, и коммитится отдельным коммитом. Каталог схем попадает в git.

### DownloadDao

- `getActiveDownloads()` → `WHERE state IN ('downloading', 'verifying')`. Сейчас запрос включает `completed`, из-за чего завершённые загрузки навсегда остаются в разделе «Загрузки».
- `observeReady(): Flow<List<DownloadEntity>>` → `WHERE state IN ('ready', 'completed') AND localPath IS NOT NULL ORDER BY completedAt DESC`. `completed` в условии — защита от строк, которые миграция не покрыла.
- `observeByBuildId(buildId): Flow<DownloadEntity?>`
- `getAllReady(): List<DownloadEntity>` — для «Очистить всё»
- `delete(buildId)` — уже существует

## Модуль core/downloads

Новый Gradle-модуль `:core:downloads`. Причина: удаление скачанного файла нужно и экрану сборки, и экрану «Мои сборки». Без общего модуля пришлось бы делать зависимость `feature:mine → feature:build-detail` либо дублировать работу с файлами.

Содержимое:

- `DownloadState` — переносится из `feature/build-detail` (sealed interface: `Idle`, `Downloading`, `Verifying`, `ReadyToInstall`, `Failed`)
- `DownloadRepository` — наблюдение по имени работы, отмена, удаление файла и строки, подсчёт суммарного размера

`DownloadWorker` **не переносится** — остаётся в `feature/build-detail` по причине из таблицы инвариантов. Постановка работы в очередь тоже остаётся в `feature/build-detail`, поскольку требует ссылки на класс воркера.

Зависимости: `feature:build-detail → core:downloads`, `feature:mine → core:downloads`.

### Наблюдение состояния

```
observeDownload(buildId): Flow<DownloadState> =
  combine(
    workManager.getWorkInfosForUniqueWorkFlow("download_$buildId"),
    downloadDao.observeByBuildId(buildId)
  ) { infos, entity ->
    последняя WorkInfo и строка БД → DownloadState
  }
```

`getWorkInfosForUniqueWorkFlow` возвращает список. Правило выбора записи детерминированное: если есть запись в незавершённом состоянии (`!state.isFinished`), берётся она; иначе берётся первая в списке. Двух незавершённых записей под одним именем быть не может — это гарантирует сам механизм уникальной работы.

Правила отображения:

- `RUNNING` → `Downloading(progress, bytesLoaded)` из `WorkInfo.progress`
- `ENQUEUED` / `BLOCKED` → `Downloading(0f, 0)`
- строка в состоянии `ready`/`completed` и файл существует на диске → `ReadyToInstall(localPath)`
- `FAILED` → `Failed`
- `CANCELLED`, отсутствие работы и готового файла → `Idle`

Проверка `File.exists()` обязательна: файлы лежат в `cacheDir`, и система вправе очистить каталог. Строка без файла считается устаревшей и удаляется.

### Сверка «зависших» загрузок

Строка может остаться в состоянии `downloading` навсегда, если процесс воркера был убит. Строки в состоянии `downloading`/`verifying`, для которых нет активной работы в WorkManager, переводятся в `failed`. Иначе они вечно висят в разделе «Загрузки».

Точка вызова: метод `DownloadRepository.reconcileStaleDownloads()`, вызываемый из `AppApplication.onCreate()` в скоупе приложения. Не в `MineViewModel` — сверка нужна независимо от того, открывал ли пользователь этот экран.

## DownloadWorker

Изменения внутри класса (FQN и ключи сохраняются):

- Проверка контрольной суммы переносится в воркер: `downloading → verifying → ready`. Сейчас проверка выполняется в `map` у flow, то есть 14 МБ перечитываются и хэшируются при каждом заходе на экран.
- При несовпадении суммы файл удаляется, пишется `failed`, возвращается `Result.failure()` — повтор не поможет, проблема на стороне артефакта.
- Запись прогресса в БД троттлится (не чаще раза в 250 мс). Сейчас `upsert` выполняется на каждые 8 КБ — около 1700 записей на 14 МБ.
- В строку записываются `versionName`, `versionCode`, `channel`, приходящие через `inputData` новыми ключами. Ключи добавляются, существующие не меняются; отсутствие новых ключей у работ, поставленных до обновления, обрабатывается значениями по умолчанию.

## BuildDetailViewModel

- В `init` — подписка на `observeDownload(buildId)`, результат кладётся в `downloadState`. Это восстанавливает индикатор при возврате на экран.
- Нажатие кнопки только ставит работу в очередь. Состояние приходит из подписки, а не из flow, возвращённого функцией постановки. Это устраняет «мёртвую» кнопку.
- Если файл уже скачан — кнопка сразу «Установить», повторная загрузка не запускается.
- **Автозапуск установщика только для загрузки, начатой в текущей сессии.** Флаг взводится при постановке в очередь и сбрасывается после запуска. Без него системный установщик будет открываться сам при каждом заходе на экран с готовым файлом.
- Отмена: `cancelUniqueWork` плюс удаление частично скачанного файла и строки.

## MineScreen — раздел «Скачанные»

Располагается между «Загрузки» и «История установок». Пустой раздел не показывается.

- Заголовок секции: `Скачанные · 42 МБ` и текстовая кнопка «Очистить всё» с диалогом подтверждения.
- Карточка: `v1.2.3 (45)`, канал, размер файла, дата загрузки, иконка удаления справа.
- Тап по карточке — переход на экран сборки (`onBuildClick`).
- Удаление одного файла — без диалога, действие дешёвое и обратимое повторной загрузкой.

### Деградация для старых записей

У строк, созданных до обновления, `versionName` пустой, а `versionCode` равен нулю. Порядок подстановки:

1. Если `versionName` не пустой — показываем его.
2. Иначе пробуем `buildDao.getBuildById(buildId)` — сборка может быть в кэше.
3. Иначе показываем нейтральную подпись «Сборка <первые 8 символов buildId>».

Размер файла всегда берётся с диска, а не из `totalBytes`, — он достоверен для любых строк. Обращение к файловой системе выполняется в `MineViewModel` на `Dispatchers.IO` при формировании состояния, а не в composable-функции.

## Тестирование

Регрессионные тесты на баг №1:

- `BuildDetailViewModelTest`: при активной работе WorkManager новая ViewModel получает `Downloading`, а не `Idle`.
- `BuildDetailViewModelTest`: повторное нажатие кнопки при идущей загрузке не приводит к застреванию в `Idle`.
- `BuildDetailViewModelTest`: при готовом файле кнопка ведёт себя как «Установить», повторная загрузка не ставится.
- `BuildDetailViewModelTest`: установщик не запускается автоматически при восстановлении `ReadyToInstall`.

Обратная совместимость:

- Тест миграции 1 → 2 (`MigrationTestHelper`, Robolectric — в `core/database` он уже используется): новые колонки добавлены, `completed` с непустым `localPath` стал `ready`, `completed` с пустым — `failed`, существующие строки не потеряны. Если `MigrationTestHelper` окажется неудобным без инструментальных тестов, запасной вариант — создать БД версии 1 сырым SQL и применить миграцию вручную.

Раздел «Скачанные»:

- `DownloadDaoTest`: `getActiveDownloads()` не возвращает `ready`; `observeReady()` возвращает и `ready`, и `completed`.
- `MineViewModelTest`: удаление убирает элемент из списка и уменьшает суммарный размер; «Очистить всё» опустошает раздел.
- `MineViewModelTest`: строка с отсутствующим на диске файлом не попадает в раздел.

## Вне scope

- **`packageName` всегда пустой.** В `BuildResponse` нет поля `package_name`, и `BuildDetailRepositoryImpl.toUi()` подставляет `""`. Из-за этого `GetInstallStatusUseCase` всегда возвращает `NotInstalled`, и кнопка никогда не покажет «Обновить» или «Установлена актуальная версия». Требует поля от бэкенда, чинится отдельной задачей.
- Автоудаление файлов любого вида — сознательно отклонено пользователем.
- Уведомление о ходе загрузки в шторке (`setForeground`).
